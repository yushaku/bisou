# ADR 0009: Kind notes are gated in SQL, cool for 8 hours, and close into a journal entry both partners own

Status: accepted (November 2026); send, cool-down and push superseded by [0012](0012-kind-notes-delivery-chosen-by-the-writer.md). Replaces the unreleased "letters gated in SQL and photo reuse" version of this ADR; time capsule letters never shipped.

## Context
A partner writes a kind note ("Lời nhắn nhỏ") to the other in four parts: what happened, I feel, because to me, I hope ([notes spec](../product/notes.md)). Every note waits at least 8 hours after it is first saved; edits never restart the wait. Then the writer rereads it and sends it, and may still edit it until the recipient opens it. The recipient learns only that a note waits, opens it when ready ("Mình sẵn sàng nghe"), and closes it with one of three answers and an optional line. A closed note becomes a journal entry of both partners: either can edit its four parts, the answer, the line and the day, and either can delete it, an exception to the journal's author-only edit and delete. A note withdrawn or never opened never reaches the journal. The recipient gets a push when a note arrives and one reminder 3 days later if it is still unopened, on the partner's journal switch and within quiet hours ([ADR 0007](0007-web-push.md)). Text only, no photos. Migrations are additive only; `0012_letters.sql` was never applied remotely and the notes migration is `0013_notes.sql`.

## Decision
- One table `notes` in migration `0013_notes.sql`, after the shipped `0012_garden_levels.sql`; the unreleased `0012_letters.sql` is dropped: `couple_id`, `writer_id`, `recipient_id` (the writer's partner, taken from the session's couple, never from the request), `happened`, `feel`, `need`, `hope` (each 1 to 500 characters, CHECK), `pick` (`try`, `talk` or `differ`), `line` (up to 500), `created_at`, `updated_at`, `sent_at`, `opened_at`, `closed_at`, `notified_at`, `reminded_at`. CASCADE with the couple and both users. No photo column.
- The `notes` row stays the only copy of a note's words for its whole life, closed included. The same migration adds `journal_entries.note_id` (nullable, `REFERENCES notes ON DELETE CASCADE`, unique when set). A closed note's entry row holds the feed position (`entry_date`, `created_at`), `author_id` = writer and an empty `body`; the journal list joins the note's parts, answer and line and returns them as `entry.note`, and the client renders them in the viewer's language with both names.
- States are derived, never stored as a word: draft (`sent_at` NULL; sendable once `created_at + 8 h` has passed), sent, opened, closed. Withdrawn means the row is deleted.
- Every recipient-facing query enforces the gate in SQL. The open-notes list selects only `sent_at IS NOT NULL AND closed_at IS NULL`, so drafts are absent from rows, counts and ordering, and the four parts are selected only `CASE WHEN opened_at IS NOT NULL`. An unopened note reaches the recipient as `{ id, state: "waiting" }`: no times, no length, no weight, so an edit after sending is invisible until opened. Open is `POST /api/notes/:id/open`, one `UPDATE ... SET opened_at = COALESCE(opened_at, now) WHERE id = ? AND recipient_id = ? AND sent_at IS NOT NULL AND closed_at IS NULL RETURNING`; a draft, a closed note, someone else's note and a missing id give the same 404.
- Writer actions before the close match `writer_id = me`. Edit is one `UPDATE ... WHERE opened_at IS NULL`, so a save that reaches D1 after the recipient opened changes nothing and answers 409. Send writes the reread text and `sent_at` in one statement guarded by `sent_at IS NULL AND created_at <= now - 8 h`. Withdraw is `DELETE ... WHERE opened_at IS NULL`. Open, edit and withdraw are single conditional statements, so whichever reaches D1 first wins.
- Close is `POST /api/notes/:id/close` by the recipient, one `db.batch` (one transaction): `UPDATE notes SET pick, line, closed_at WHERE id = ? AND recipient_id = ? AND opened_at IS NOT NULL AND closed_at IS NULL`, then `INSERT INTO journal_entries (..., author_id = writer, entry_date = today in Vietnam, created_at = now, body = '', note_id) SELECT ... FROM notes WHERE id = ? AND closed_at IS NOT NULL AND NOT EXISTS (SELECT 1 FROM journal_entries WHERE note_id = ?)`. A second close changes nothing and gets 404. The insert is not `OR IGNORE`: a failed insert must roll back the close, never leave a closed note without its entry; the unique `note_id` is the backstop. Nothing is copied from the note, so a close has no read-then-write.
- After the close, either member of the couple edits through `PUT /api/notes/:id/closed` (parts, answer, line, day; one batch updating `notes` and the entry's `entry_date`) and deletes through `DELETE /api/notes/:id`, which removes the note and, by CASCADE, its entry. The journal's own `PUT` and `DELETE /api/journal/:id` answer 404 for an entry with `note_id`, so author-only rules stay untouched for every other entry and no photo can be attached to a note entry.
- Push, on devices with `journal = 1`, payload `{ title, url: "/journal?section=notes", tag: "notes" }` with the writer's name only:
  - send outside quiet hours sets `notified_at = now` in the send statement and pushes with `ctx.waitUntil`; send inside quiet hours leaves `notified_at` NULL; edits never push;
  - the 07:00 cron run claims `UPDATE notes SET notified_at = ? WHERE notified_at IS NULL AND sent_at <= ? RETURNING` and pushes only the unopened ones, one message per recipient with a count;
  - the same run claims the reminder, `UPDATE notes SET reminded_at = ? WHERE reminded_at IS NULL AND opened_at IS NULL AND sent_at < (00:00 Vietnam time two days before today) RETURNING`: a note sent on Vietnam day D is reminded once at 07:00 on D + 3;
  - `releaseNightJournal` skips entries with `note_id`, and close never calls `notifyJournal`. The writer gets no push.

## Consequences
- A missed 07:00 run sends the held arrival and the reminder on the next 07:00 run, still only for unopened notes; claims make a repeated run send nothing twice. A send whose push fails is not retried; the Home inbox tile still shows the note.
- Delivery is at most once per note per kind, not per device. Note sends share the 07:00 invocation's subrequests with the night journal release.
- The journal list does one extra primary-key lookup for the notes on a page. A note entry carries no photos and no body text; clients that ignore `entry.note` would show an empty card, so every client renders it.
- Accepted leak: a withdrawn note disappears from the recipient's list and the Home tile after the push announced it.
- Notes are personal data about the relationship: never logged (logs carry counts only), deleted with the writer, recipient or couple, and joining export, unpairing and account deletion when those ship.
- A local D1 that applied `0012_letters.sql` keeps a `letters` table and `photos.letter_id`; delete the local D1 state and apply the migrations again instead of shipping a migration that drops them.

## Superseded in part (November 2026)

The PO cancelled quiet hours. The text above is kept as written; where it differs, this note wins.
- A note send always sets `notified_at = now` and pushes at once, at any hour. The 07:00 cron keeps `RELEASE_NOTES_SQL` only to flush notes still held with `notified_at` NULL (for example at deploy time), and keeps the reminder claim.
- Every push has a fixed TTL of 24 hours.
- `releaseNightJournal` no longer exists, so the shared 07:00 subrequest budget note no longer applies; `journal_slot` and `journal_entries_created` stay in the schema, unused.
